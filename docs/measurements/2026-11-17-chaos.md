# 장애 실험 (2026-11-17)

- 목적: 일정 부하 중에 Redis·앱 1개·MySQL을 하나씩 멈추고, 손님이 받는 응답, 회복까지 걸린 시간, 끝난 뒤의 정합성(초과 예약 0, Redis = DB, 아웃박스 미발행 0)을 확인한다
- 해석과 결정: `docs/decisions.md` 6장 "장애 실험"·"아웃박스 실패 한도"·"업무 지표"
- 원본: `load/chaos.sh`가 만든 `load/results/chaos-20261117-012202/`(실험마다 k6 CSV·summary JSON·로그·이벤트 시각·초별 응답 코드 `*.timeline.tsv`, `summary.md`. 저장소에는 넣지 않음). 503 수정 전 1회차는 `chaos-20261117-005417/`

## 환경

Mac(Intel i7-9750H 6코어 12스레드, 32GB), macOS 26.7, Docker Desktop 29.8.2(VM 12 CPU, 8GB). 앱 3개(각 768MB, HikariCP 풀 10) + Nginx + MySQL 8 + Redis 7(AOF) + Prometheus + Grafana + k6가 한 VM에서 함께 돈다. 측정한 작업 트리는 `c1576ed` + 이 브랜치의 변경(아웃박스 실패 한도, 업무 지표, DB 연결 장애 503).

## 방법

`./load/chaos.sh` (기본값: 초당 20건 × 180초, 부하 시작 30초 뒤 장애, 취소 비율 0.2)

- 부하: `steady.sh --scenario spread`. 손님 10,000명이 판매일 5개 × 빵 20종(총량 각 500)에 1개씩 예약. 매진되지 않는 성공 경로
- 취소: 반복마다 0.2 확률로 그 VU가 앞서 만든 예약 하나를 취소한다(`CANCEL_RATIO`). 방금 만든 예약이 아니라 쌓아 둔 예약이라 Redis 장애로 예약이 모두 503인 동안에도 취소가 들어가고, 재고 복구가 아웃박스에 쌓인다
- 실험마다 Nginx를 다시 시작하고(앞 실험의 `max_fails` 상태를 비움), 시드를 다시 넣는다
- 장애
  - **redis-pause**: `docker compose pause redis` → 30초 → `unpause`
  - **app2-kill**: `docker compose kill app2` → 20초 → `start`(healthy까지 기다림)
  - **mysql-restart**: `docker compose restart mysql`(정상 종료 → 시작, healthy까지 기다림)
- 응답: k6 CSV(요청마다)에서 초 단위로 센다. 연결 실패는 k6 status 0. "다른 앱으로 넘김"은 `X-Upstream`에 주소가 둘 이상인 응답(Nginx가 연결 실패로 다음 앱에 다시 보냄). 응답한 앱은 마지막 주소
- 판정: 부하가 끝난 뒤 2초마다 최대 120초. 이 실험의 5일치 100행에서 ① `reserved_qty` = 예약 수량 합 ≤ `reservable_qty` ② 키가 있는 행마다 Redis 잔여 = DB 잔여 ③ `published_at IS NULL` 행 0(dead는 따로)

## 예상과 다르게 나온 것

| # | 관찰 | 원인 | 처리 |
|---|---|---|---|
| ① | Redis를 멈춘 동안 실패한 아웃박스 행(93건, attempts 1)의 재고 복구가 폴러보다 먼저 반영돼 있었다. 같은 일로 `OutboxDeadLetterTest`가 실행마다 Redis 3 또는 5로 갈렸다 | `docker pause`는 프로세스를 얼릴 뿐 TCP 연결을 끊지 않는다. 클라이언트(Lettuce)에서 2초 시간 초과로 끝난 명령이 소켓 버퍼에 남아 있다가 unpause 직후 실행된다. `redis-cli`로 따로 확인: pause 중 보낸 `SET`이 클라이언트는 시간 초과(exit 124)인데 재개 뒤 값이 들어가 있었다 | 아웃박스는 `applied` 키로 멱등이라 늦게 실행돼도 두 번 더해지지 않는다(정합성 판정 통과). 테스트는 재개 뒤 밀린 명령을 비우고 재고를 "복구 못 한" 값으로 되돌려 고정했다. 예약은 Redis에 처음 닿는 명령(요청 제한)에서 시간 초과가 나 그 뒤 명령을 보내지 않으므로 Redis 재고는 바뀌지 않는다. 남는 한계는 decisions.md 6장 "장애 실험" |
| ② | MySQL 재시작 순간 예약·취소 30건이 **500 `INTERNAL_ERROR`** (1회차) | 끊긴 커넥션으로 트랜잭션을 열다 `CannotCreateTransactionException`(SQLSTATE 08S01)이 났고, 처리하지 못한 예외로 떨어졌다. Redis 장애는 503인데 DB 연결 장애는 500이었다 | **고침**: `ApiExceptionHandler`가 `DataAccessResourceFailureException`·`CannotCreateTransactionException`도 503 `SERVICE_UNAVAILABLE`로 응답한다. 2회차(위 표)는 같은 30건이 503. E-12(Redis 차감 뒤 DB 저장 실패)도 연결 장애면 503으로 바뀐다(`docs/edge-cases.md`) |
| ③ | Redis 재개 뒤에도 아웃박스 발행이 최대 57초 늦었다(장애 시작 기준) | 폴러는 ShedLock(Redis)을 잡아야 돈다. pause 중 시간 초과로 끝난 락 명령도 ①처럼 재개 뒤 실행돼, 아무도 쓰지 않는 락이 `lockAtMostFor` 30초까지 남았다 | 이미 알던 한계(decisions.md 6장 "아웃박스와 Redis 장애", 2026-11-07 약 35초)와 같은 원인. 그사이 미발행이 0보다 크지만 5분보다 짧아 경고는 뜨지 않는다. 고치지 않음 |
| ④ | MySQL 재시작 때 503 뒤 약 3초 동안 응답이 하나도 없었다 | 앱이 새 커넥션을 기다린다(Hikari `connectionTimeout` 30초). MySQL이 그 안에 돌아와 기다리던 요청이 모두 성공했다 | 기대한 동작. 30초보다 긴 DB 장애에서는 그 요청들이 30초 뒤 503이 된다(이번에는 재지 않음) |

예상대로였던 것: Redis 장애 중 예약 503(Q-05)·취소 200(DB만으로 성공, Redis 시간 제한 두 번만큼 약 4초), 앱 1개 다운 때 Nginx가 연결 실패를 다른 앱으로 넘겨 5xx 0(POST라도 연결 단계 실패는 다시 보냄), 세 실험 모두 초과 예약 0·Redis = DB·미발행 0·dead 0.

## 한계

- 실험마다 1회만 돌렸다. 숫자(503 건수, 복귀 18초 등)는 이 환경의 한 번 값이다
- 노트북 한 대의 Docker VM 안에서 잰 값이다. `docker pause`는 "응답 없는 Redis"를, `kill`은 "갑자기 사라진 앱"을, `restart`는 "정상 종료 후 재시작"을 흉내 낸다. 네트워크 단절·디스크 장애·Redis 데이터 유실(AOF 없이 재시작)은 다루지 않았다
- 초당 20건은 장애 중 동작을 보려는 낮은 부하다. 피크(동시 1,000건) 중 장애는 재지 않았다
