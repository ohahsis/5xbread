# 예약 v1/v2 비교 측정 (2026-11-16)

- v1: `fivexbread.reservation.mode=db-only`. 재고·1인 한도·하루 건수 검사를 DB로 한다(회원 행 `FOR UPDATE` → 건수·합계 → 조건부 UPDATE). 요청 제한·Idempotency·예약번호는 v2와 같이 Redis를 쓴다
- v2: `redis`(기본·운영). Redis Lua로 검사·차감 → DB 조건부 UPDATE로 확정
- 해석과 결정: `docs/decisions.md` 6장 "예약 v1/v2 비교"·"예약 측정 모드"
- 원본: `load/compare.sh`가 만든 `load/results/20261116-160918/`(k6 summary JSON, `prometheus.tsv`, `summary.md`. 저장소에는 넣지 않음). Grafana 스크린샷은 `docs/measurements/images/`에 직접 캡처해 넣는다

## 환경

Mac(Intel i7-9750H 6코어 12스레드, 32GB), macOS 26.7, Docker Desktop 29.8.2(VM 12 CPU, 8GB). 앱 3개(각 `mem_limit` 768MB, HikariCP 기본 풀 10) + Nginx + MySQL 8 + Redis 7 + Prometheus + Grafana + k6가 한 VM에서 함께 돈다. 같은 VM에 다른 compose 스택(앱 3개 등 6개 컨테이너, 요청 없음)도 떠 있었다. 측정한 작업 트리는 `0197f3d` + 이 브랜치의 변경.

## 방법

`./load/compare.sh --rate-spread 500 --rate-hot 150 --rounds 3`

- v1 → v2를 번갈아 3라운드(v1 v2 v1 v2 v1 v2). 모드를 바꿀 때마다 앱 3개를 다시 만든다
- 라운드마다 워밍업 1회(`run.sh` + spread 20초)를 버리고 세 시나리오를 잰다
  - **burst**: `run.sh`. 손님 1,000명이 같은 순간 빵 1개(총량 120)를 예약. 처리량은 1,000 ÷ 가장 늦은 응답 시간
  - **spread**: `steady.sh --scenario spread`. 초당 500건 × 60초, 판매일 5개 × 빵 20종(총량 각 500)에 나눔. 모두 성공 경로
  - **hot**: `steady.sh --scenario hot`. 초당 150건 × 60초, 한 판매일의 빵 1 한 행(총량 500, 스키마 상한)에 몰림. 약 3초 만에 매진되고 그 뒤로는 매진 409. 처리량은 201·409 응답 수 ÷ 60
- 손님 10,000명(`seed-steady.sql`)은 측정 전에 실제 로그인 API로 로그인해 두고, 측정 구간에는 예약 요청만 보낸다
- 시드는 측정마다 다시 넣고 그 판매일의 Redis 키를 지운다(v2는 첫 요청 때 DB 기준으로 적재)
- k6 `constant-arrival-rate`, 최대 VU 1,000. 응답이 늦어 VU가 모자라면 보내지 못한 요청이 `dropped`로 남는다

## N 정하기 (v1, 30초씩 올림)

시나리오마다 v1이 무너지기 시작하는 초당 건수를 N으로 했다. 30초 일정 부하를 같은 기동에서 이어서 돌렸다(앞 단계가 워밍업이 됨).

| spread 초당 | p95 ms (1회 / 2회 / 3회) | Hikari pending 최대 | dropped |
|---|---|---|---|
| 100 | 51 / 50 / 22 | 0 | 0 |
| 200 | 50 / 50 / 34 | 0 | 0 |
| 300 | 73 / 73 / 40 | 0~2 | 0 |
| 400 | 161 / 129 / 52 | 0~39 | 0 |
| 500 | 878 / 1,294 / 468 | 72~179 | 0~15 |
| 600 | 2,503 / - / - | 190 | 2,182 |

| hot 초당 | p95 ms (1회 / 2회) | Hikari pending 최대 | 비고 |
|---|---|---|---|
| 100 | 17 / 17 | 0 | |
| 200 | 725 / 681 | 23~33 | |
| 300 | 1,513 / 1,386 | 117~141 | dropped 151~171 |
| 350 | 1,908 / - | 162 | **5xx 222** |
| 400 이상 | 2,100 이상 | 190 | 5xx 1,645 이상 |

- spread: 400까지는 p95가 0.2초 아래이고, 500에서 pending이 쌓이며 p95가 0.5~1.3초로 뛴다 → **N = 500**. 요청 수는 손님 10,000명 × 하루 3건 = 30,000건까지라 60초면 500이 상한이기도 하다
- hot: 100은 멀쩡하고 200에서 p95가 0.7초로 뛴다 → 그 사이인 **N = 150**. 150 × 60초 = 9,000건이라 아래 예약번호 상한(9,999)에도 걸리지 않는다
- hot 350 이상의 5xx는 DB 경합이 아니라 **v1의 예약번호 소모** 때문이다. v1은 재고 검사보다 먼저 예약번호를 받아 409로 끝난 요청도 번호를 쓰므로, 한 판매일에 요청이 9,999건을 넘으면 `판매일 예약번호가 9999를 넘음`으로 500이 된다(v2는 Redis를 통과한 요청만 번호를 받는다)
- 앱을 막 다시 만든 직후에는 같은 비율에서도 훨씬 나빴다(hot 125·150·175의 p95 1.2~1.7초, spread 450은 dropped 5,120). 그래서 compare.sh의 워밍업에 일정 부하 20초를 넣었다

## 측정의 한계

- spread 500/s는 N을 정할 때(30초, 앞 단계로 데워짐)보다 compare.sh(60초)에서 두 모드 모두 훨씬 나빴다(dropped 4,000~10,000). 같은 조건에서 번갈아 잰 값끼리만 비교한다
- hot 150/s에서 v1은 탐색 때와 달리 무너지지 않았다(p95 50~431ms). 무너지기 시작하는 지점이 150~200 사이라 회차마다 흔들린다
- 측정 구간의 Prometheus 값은 측정 끝 시각에서 거슬러 읽었다. 이번 실행에서는 그 구간을 10초 넓게 잡아 burst 구간에 직전 워밍업의 끝이 섞였고(burst의 pending은 예약 순간에도 앱마다 160~170이라 결론은 같음), v1-r2 hot·v2-r3 spread는 토큰 재로그인이 구간에 들어가 Redis 명령 수가 부풀었다. 두 가지 모두 compare.sh에서 고쳤다(구간을 넓히지 않음, 모드마다 10분 넘은 토큰을 미리 갱신). 응답 시간·처리량(k6)은 영향을 받지 않는다
