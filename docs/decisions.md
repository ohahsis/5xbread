# 결정 기록 (decisions.md)

[요구사항 정의서](./requirements.md)와 다르게 정했거나, 정의서가 열어 둔 질문에 답한 내용을 모읍니다. **정의서와 이 문서가 다르면 이 문서가 우선**합니다.

결정이 바뀌면 해당 항목을 고치고 맨 아래 "변경 이력"에 한 줄 남깁니다.

---

## 1. 기술 버전

| 항목 | 결정 | 이유 |
|---|---|---|
| Java | 21 (LTS) | 정의서와 동일. Boot 3.5와 검증된 조합 |
| Spring Boot | 3.5.16 | 3.x 라인의 마지막 오픈소스 릴리스(2026-06-25). 익숙한 3.x 생태계와 라이브러리 호환성을 우선 |
| 빌드 | Gradle 8.14.x (Kotlin DSL) | Boot 3.5가 지원하는 Gradle 8 라인으로 고정 |
| DB / 캐시 | MySQL 8.0, Redis 7 | 정의서와 동일 |

**Boot 3.5를 고르면서 감수한 것**

- 3.x는 오픈소스 지원이 2026년 6월 30일에 끝나, 이후 보안 패치가 무료로 나오지 않음. 1차 개발 범위에서는 영향이 없고, 2차 이후 Boot 4 마이그레이션을 별도 작업으로 검토
- start.spring.io는 지원 중인 버전(4.x)만 제공하므로, 빌드 파일은 직접 작성
- Java 21의 가상 스레드는 `synchronized` 블록 안에서 블로킹하면 캐리어 스레드에 고정(pinning)됨 → 락이 필요하면 `ReentrantLock` 사용
- QueryDSL은 3.5에서도 쓸 수 있지만 1차에서는 쓰지 않음 (아래 4장)

## 2. 저장소·개발 환경

| 항목 | 결정 |
|---|---|
| 저장소 구조 | 모노레포. `backend/`(Spring), `frontend/`(2차), `infra/`, `load/`, `docs/` |
| 로컬 인프라 | `compose.yaml`: MySQL·Redis만. 앱은 IDE에서 실행. Spring Docker Compose Support가 접속 정보를 자동 연결 (`spring.docker.compose.file=../compose.yaml`) |
| 앱 3개 구성 | `compose.full.yaml`: app1~3 + Nginx. 앱 3개 작업 때 Dockerfile과 함께 추가 |
| 비밀 값 | `.env`(git 제외)에 두고 `.env.example`에 키 이름만 커밋 |
| 사장님 초기 계정 | Flyway SQL이 아니라 `ApplicationRunner`로 생성. ADMIN이 없으면 `.env`의 `ADMIN_INITIAL_PASSWORD`를 BCrypt로 해시해 만들고 `must_change_password=true` |
| 테스트 손님 1,000명 | `local` 프로필 전용 마이그레이션 위치에만 둠 (운영에는 들어가지 않게) |
| 브랜치 | `main` 보호(PR로만 merge, squash merge). 작업 브랜치는 `feat/{기능ID}-{이름}`, `fix/`, `chore/`, `test/` |

## 3. 시간 처리 규칙

| 위치 | 타입·형식 |
|---|---|
| DB | `DATETIME`, KST로 저장 |
| 엔티티 | `LocalDateTime` / `LocalDate` |
| API 요청·응답 | `OffsetDateTime`, `+09:00` 오프셋 포함 |
| 현재 시각 | 주입한 `Clock`(`ZoneId.of("Asia/Seoul")`)만 사용. `LocalDateTime.now()` 직접 호출 금지 |

MySQL 컨테이너는 `--default-time-zone=+09:00`, 문자셋은 `utf8mb4`로 띄웁니다.

## 4. 1차 개발 범위 (2026-10-15 ~ 10-22)

백엔드 P0 전부와 동시성·분산 핵심을 1주 안에 구현합니다. 프론트엔드는 2차에서 OpenAPI 명세를 바탕으로 만듭니다.

### 포함

| 묶음 | 기능 |
|---|---|
| 환경 | Flyway V1·V2, 공통 예외(RFC 9457 + `code`), Testcontainers, GitHub Actions CI |
| 인증·회원 | C-01, AU-01~AU-10 (가입, 로그인 JWT + Refresh rotation, 실패 잠금, 권한), C-09·A-09 임시 비밀번호, C-10 |
| 사장님 관리 | A-01 빵 등록·수정·판매 중지, A-04 판매일 설정, A-02 수량 설정(R-07, ETag/If-Match) |
| 조회 | C-02 빵 목록(Caffeine 로컬 캐시 + Redis 잔여), 판매일·픽업 시간대 조회 |
| 예약 | C-04 예약(Redis Lua → DB 조건부 UPDATE → 보상, Idempotency-Key, 요청 제한), C-06·A-08 취소, C-05 내 예약 목록(커서)·상세, A-06 수령 처리 |
| 실시간·분산 | C-03 WebSocket + Redis Pub/Sub, 앱 3개 + Nginx 구성 |
| 배치 | A-07 노쇼 처리 + R-17 (ShedLock), N-05 정합성 점검, A-12 수량 재계산(API만) |
| 테스트 | 동시 예약 1,000건 초과 0건, E-01~E-15 엣지 케이스 |

### 정의서와 다르게 단순화

| 정의서 | 1차 구현 | 이유 |
|---|---|---|
| 트랜잭셔널 아웃박스(`outbox_event`) | `@TransactionalEventListener(AFTER_COMMIT)` + 5분 정합성 점검으로 보정 | 이벤트 유실 시에도 "덜 팔리는" 방향으로만 어긋나고 점검이 복구함. 테이블은 V1에 만들어 두고 2차에서 적용 |
| QueryDSL (관리자 검색) | Spring Data JPA 쿼리 메서드·`@Query` | 1주 범위의 검색 조건이 단순해 설정 비용이 더 큼 |
| 사진 800×800 WEBP 변환 | 매직 바이트 검사 + UUID 파일명 저장만 | 변환은 2차 |
| A-07 픽업 QR | HMAC 서명 토큰 API만 (QR 이미지는 프론트) | |
| 예약 v1(DB만) vs v2(Redis) 비교 측정 | 바로 Redis 방식으로 구현 | 비교 측정은 2차 부하 테스트에서 |

### 2차로 미룸

- 프론트엔드 (손님 11개, 사장님 11개 화면)
- A-03 수량 복사 (화면 기능이라 프론트와 함께)
- A-05 대시보드 실시간 구독, 픽업 준비 목록 인쇄
- A-10 회원 관리 화면용 검색 고도화, A-11 판매 통계·집계 배치
- C-07 픽업 확인 화면, C-08 빵 상세, C-11 예약 제한 안내 (화면)
- k6 부하 테스트, Prometheus·Grafana, 장애 실험 기록
- 오래된 예약·이력 아카이브

## 5. 열린 질문 확정 (정의서 12장)

| # | 질문 | 결정 |
|---|---|---|
| Q-01 | 예약 오픈·마감 시각 | 판매일 3일 전 10:00 오픈, 전날 20:00 마감 (사장님이 판매일마다 변경 가능) |
| Q-02 | 픽업 시간대별 인원·수량 제한 | 1차 없음 |
| Q-03 | 취소 마감이 지난 시간대 예약 허용 | 발생하지 않게 함. 마감 시각은 첫 픽업 1시간 전까지만 설정 가능 |
| Q-04 | 노쇼 제재 기준 | 최근 30일 안 2회 → 14일 예약 제한, 사장님 해제 가능 |
| Q-05 | Redis 장애 시 | 예약 API 503으로 중단. 복구 후 DB 기준으로 잔여를 재적재한 뒤 재개 |
| Q-06 | 선결제 | 없음 (현장 결제) |
| Q-07 | 예약 1건 최대 수량 | 빵 합계 20개 |
| Q-08 | 남은 예약 수량을 현장 판매로 전환 | 1차 없음 (사장님이 총량을 직접 줄임, R-07 범위 안에서) |
| Q-09 | 입장 대기열 | 1차 없음. 부하 테스트 결과를 보고 결정 |
| Q-10 | 1년 지난 데이터 보관 | 1차 없음. 2차에서 월별 파티션 + 아카이브 검토 |
| Q-11 | pod당 CPU·메모리 | 부하 테스트 후 결정 |
| Q-12 | 다중 계정 견제 | IP당 하루 가입 10회 제한 + 픽업 때 이름·번호 확인. 본인 인증은 도입하지 않음 |
