# 결정 기록 (decisions.md)

[요구사항 정의서](./requirements.md)와 다르게 정했거나, 정의서가 열어 둔 질문에 답한 내용을 모읍니다. **정의서와 이 문서가 다르면 이 문서가 우선**합니다.

결정이 바뀌면 해당 항목을 고치고 맨 아래 "변경 이력"에 한 줄 남깁니다.

## 1. 기술 버전

| 항목 | 결정 | 이유 |
|---|---|---|
| Java | 21 (LTS) | 정의서와 동일. Boot 3.5와 검증된 조합 |
| Spring Boot | 3.5.16 | 3.x 라인의 마지막 오픈소스 릴리스(2026-06-25). 익숙한 3.x 생태계와 라이브러리 호환성을 우선 |
| 빌드 | Gradle 8.14.x (Kotlin DSL) | Boot 3.5가 지원하는 Gradle 8 라인으로 고정 |
| DB / 캐시 | MySQL 8.0, Redis 7 | 정의서와 동일 |

**Boot 3.5를 고르면서 감수한 것**

- 3.x는 오픈소스 지원이 2026년 6월 30일에 끝나, 이후 보안 패치가 무료로 나오지 않음. 1차 개발 범위에서는 영향이 없고, 2차 이후 Boot 4 마이그레이션을 별도 작업으로 검토
- start.spring.io는 지원 중인 버전(4.x)만 제공하므로, 빌드 파일은 직접 작성
- Java 21의 가상 스레드는 `synchronized` 블록 안에서 블로킹하면 캐리어 스레드에 고정(pinning)됨 → 락이 필요하면 `ReentrantLock` 사용
- QueryDSL은 3.5에서도 쓸 수 있지만 1차에서는 쓰지 않음 (아래 4장)

## 2. 저장소·개발 환경

| 항목 | 결정 |
|---|---|
| 저장소 구조 | 모노레포. `backend/`(Spring), `frontend/`(손님 화면, React + Vite), `infra/`, `load/`, `docs/` |
| 패키지 구조 | **정의서 13장 "패키지 구조"(기능별 패키지)와 다르게**(2026-11-24, #27) 역할로 먼저 나눈다. `inbound.controller.{도메인}`(컨트롤러, 아래 `model.request`·`model.response`), `domain.{도메인}`(Facade·Service·업무 규칙·업무 설정값 `*Properties`, 아래 `model`·`model.enums`·`model.vo`·`repository`), `config`(인프라 설정만, 아래 `security`·`websocket`·`redis`·`scheduling`·`openapi`, 루트에 `ClockConfig`), `common`, `realtime`, `batch`. 이유: 기능별 패키지 하나에 컨트롤러·DTO·설정·엔티티·리포지토리가 하위 패키지 없이 섞여 있었고 파일이 늘어(`reservation` 58개, `saledate` 47개) 역할을 폴더로 구분하기 어려웠다. HTTP 입구와 설정을 업무 코드와 떼어 파일을 둘 자리를 정했다. `batch`·`realtime`은 입출력에 가까워 `domain` 밖에 둔다. 대가: 한 기능을 고칠 때 한 폴더만 보면 되는 장점(정의서의 이유)이 줄고, 패키지가 갈라져 package-private이던 일부 타입·멤버가 public이 됐다. **config 분리(2026-11-27)**: 처음에는 `@Configuration`과 `*Properties` 20개를 모두 `config` 한 곳에 두었다. 업무 설정값 9개(예약 한도, 가입·탈퇴, 로그인 잠금, 영업 시간, 재고 점검, 아웃박스 등)는 쓰는 도메인 옆(`domain.reservation`·`member`·`auth`·`saledate`, `common.outbox`)으로 옮겼다. 규칙을 고칠 때 `config`와 도메인을 오가지 않게 하고, `ReservationProperties`가 `domain.reservation`의 enum을 쓰고 도메인은 다시 `config`를 쓰던 서로 맞물린 의존을 없애기 위해서다. `config`는 도메인별(`config.reservation`)이 아니라 기술별로 나눈다. 도메인별로 나누면 `domain` 트리를 한 번 더 복제하는 셈이다. `RealtimeRedisConfig`·`CatalogCacheConfig`는 아직 기능 클래스(`StockBroadcaster`, `CatalogCacheEvictor`)를 import한다. **의존 검사(2026-11-27)**: `domain`이 `config`를 쓰던 5개 파일을 정리했다. `JwtProperties`는 `domain.auth`, `CatalogCacheProperties`는 `domain.saledate`로 옮기고(읽는 쪽이 도메인), 시간대 상수 `KST`는 `ClockConfig`에서 `common.Times`로 뺐다(`Clock` 빈은 `ClockConfig`에 그대로). 그 뒤 ArchUnit(`ArchitectureTest`)으로 ① `domain..`은 `inbound..`·`config..`을 import하지 않는다 ② `config..`은 `inbound..`을 import하지 않는다 ③ `@Transactional`이 클래스나 메서드에 붙은 클래스는 `org.springframework.data.redis..`에 의존하지 않는다를 검사한다. 처음 있던 위반(①의 `domain` → `inbound` DTO 27개 클래스, 218건)은 `FreezingArchRule`로 `backend/archunit_store`에 얼려 새 위반만 막았다. 세 단계(#31·#32·2026-11-27 reservation)로 0건이 되어 ①은 freeze를 빼고 위반 0을 강제하는 일반 규칙이 됐다. ②·③은 처음부터 위반 0건이고 freeze로 둔다. **허용 목록은 줄이기만 한다**: 위반을 고치면 ArchUnit이 목록에서 지우고, 새 규칙에 허용 목록이 조용히 생기지 않게 `allowStoreCreation=false`로 둔다. 한계: ③은 직접 의존만 본다. 트랜잭션 메서드가 Redis를 쓰는 다른 빈을 거쳐 부르는 것은 잡지 못한다. 서비스·Facade는 command·result(`domain.{도메인}.model.vo`)만 주고받고, request → command, result → response 변환은 컨트롤러·DTO가 한다. 예약 생성의 Idempotency 저장 본문은 HTTP 응답 그대로여야 해서 `ReservationFacade.create`가 응답을 만드는 함수(`ReservationResponse::from`)를 받는다 |
| 로컬 인프라 | `compose.yaml`: MySQL·Redis만. 앱은 IDE에서 실행. Spring Docker Compose Support가 접속 정보를 자동 연결 (`spring.docker.compose.file=../compose.yaml`). 자동 연결은 `application.yml`의 URL·비밀번호를 쓰지 않으므로(2026-11-18 확인) MySQL은 라벨 `org.springframework.boot.jdbc.parameters`로 운영과 같은 시간 제한·락 대기를 붙이고(Flyway도 이 URL이라 local만 socketTimeout이 붙음), Redis는 비밀번호를 넘기지 못해 `org.springframework.boot.ignore`로 자동 연결을 끄고 `spring.data.redis.*`(localhost + `REDIS_PASSWORD`)를 쓴다 |
| 앱 3개 구성 | `compose.full.yaml`: MySQL·Redis(compose.yaml과 같은 설정 + healthcheck)·app1~3(같은 이미지 `backend/Dockerfile`)·Nginx(설정 `infra/nginx/nginx.conf`, 이미지 `frontend/Dockerfile` = 손님 화면 빌드 결과를 넣은 nginx:1.27.5). 프로젝트 이름 `fivexbread-full`·볼륨을 개발용과 나누고 MySQL·Redis 포트는 열지 않아, 두 환경을 함께 띄워도 데이터·포트가 섞이지 않는다. 앱은 `docker` 프로필(아래 6장 "앱 3개 docker 프로필") |
| 비밀 값 | `.env`(git 제외)에 두고 `.env.example`에 키 이름만 커밋 |
| Redis 비밀번호·메모리 | 2026-11-18부터 `REDIS_PASSWORD` **필수**(compose 두 개 모두 `${REDIS_PASSWORD:?}`). Redis는 `--requirepass`, 앱은 `spring.data.redis.password`. 같은 네트워크의 다른 컨테이너·내 PC의 다른 프로세스가 재고·토큰 키를 읽고 쓰지 못하게. Redis 컨테이너에 `REDISCLI_AUTH`를 넣어 healthcheck와 `load/*.sh`의 `docker compose exec redis redis-cli`가 그대로 동작한다. 테스트 컨테이너도 같은 설정(`IntegrationTestSupport`, `@ServiceConnection`은 `GenericContainer`의 비밀번호를 넘기지 못해 `@DynamicPropertySource`). `--maxmemory 256mb --maxmemory-policy noeviction`: 메모리가 차면 키를 지우지 않고 쓰기를 거부한다(`OOM` → 앱 503, 6장 "저장소 장애 응답"). 재고(`stock:`)·예약번호·`user_qty` 키가 지워지면 초과 예약이나 번호 중복으로 이어지기 때문이다(기본 정책도 noeviction이지만 명시). 256MB는 지금 키 크기(판매일 × 빵 30종, Idempotency 응답 24시간, Refresh Token)에 충분한 여유로 정했고 측정한 값은 아니다. Redis 컨테이너에는 메모리 한도(`mem_limit`)가 없다(2026-11-19 확인, 호스트 메모리까지). 한도를 두게 되면 AOF 재작성·RDB 저장의 fork가 쓰기 중인 페이지를 복사(copy-on-write)하므로 maxmemory의 2배 이상(512MB 이상, 예: 768MB)으로 잡는다. maxmemory는 데이터만 세고 이 복사분과 클라이언트 버퍼는 세지 않는다 |
| 사장님 초기 계정 | Flyway SQL이 아니라 `ApplicationRunner`로 생성. ADMIN이 없으면 `.env`의 `ADMIN_INITIAL_PHONE`·`ADMIN_INITIAL_PASSWORD`(BCrypt로 해시)로 만들고 `must_change_password=true`. 값이 비었거나 형식이 틀리면 앱은 띄우고 경고만 남김. 앱 여러 개가 동시에 떠도 MySQL `GET_LOCK`으로 한 명만 생성 |
| 테스트 손님 1,000명 | **마이그레이션이 아니라 `load/seed.sql`**(부하 테스트 전에 `load/run.sh`가 실행). 운영 마이그레이션에는 넣지 않는다. 이유는 6장 "부하 테스트 데이터" |
| 브랜치 | `main` 보호(PR로만 merge, squash merge). 작업 브랜치는 `feat/{기능ID}-{이름}`, `fix/`, `chore/`, `test/`, `docs/`. 서로 의존하는 기능 묶음은 대표 ID 하나로 브랜치를 만들고, 커밋은 기능 ID별로 나누며 PR 제목에 포함 ID를 모두 적는다 (예: feat/A-01-admin-stock → [A-01·A-04·A-02])        |

## 3. 시간 처리 규칙

| 위치 | 타입·형식 |
|---|---|
| DB | `DATETIME`, KST로 저장 |
| 엔티티 | `LocalDateTime` / `LocalDate` |
| API 요청·응답 | `OffsetDateTime`, `+09:00` 오프셋 포함 |
| 현재 시각 | 주입한 `Clock`(`ZoneId.of("Asia/Seoul")`)만 사용. `LocalDateTime.now()` 직접 호출 금지 |
| JVM 기본 시간대 | `Asia/Seoul`로 고정 (앱 `main`, 테스트 `user.timezone`). Hibernate의 `jdbc.time_zone` 변환이 JVM 시간대를 기준으로 하므로, UTC인 CI·컨테이너에서 `LocalDateTime`이 9시간 밀려 저장되는 것을 막는다 |
| 시간대 설정 일치 | 네 곳을 모두 KST로 맞춘다: ① JVM(`FivexbreadApplication.main`의 `TimeZone.setDefault`, Dockerfile `TZ`·`-Duser.timezone`, 테스트 `build.gradle.kts`의 `user.timezone`) ② `spring.jpa.properties.hibernate.jdbc.time_zone: Asia/Seoul` ③ JDBC URL `serverTimezone=Asia/Seoul` ④ MySQL `--default-time-zone=+09:00`(compose 두 개, Testcontainers). 하나라도 어긋나면 JPA와 JdbcTemplate(Lua 적재·정합성 점검·배치가 쓰는 경로)이 같은 칸을 9시간 다르게 읽는다. `TimeZoneGuardTest`가 지킨다: JVM·`Clock` 시간대, JPA로 쓴 값을 JdbcTemplate로 읽기와 그 반대, 저장된 문자열, DB `NOW()`와 앱 시각 차이 1분 이내. 테스트 JVM을 UTC로 돌리면 4개 중 3개가 실패한다(JPA 09:15 → JDBC 18:15, JDBC 09:15 → JPA 00:15) |

MySQL 컨테이너는 `--default-time-zone=+09:00`, 문자셋은 `utf8mb4`로 띄웁니다.

## 4. 1차 개발 범위 (2026-10-15 ~ 11-07)

**1차 완료: 2026-11-16** (마무리 작업 chore/phase1-wrapup 포함). 남은 일은 아래 "2차로 미룸"에 모았습니다.

백엔드 1차 범위 전체를 11/7까지 구현합니다. 프론트엔드는 2차에서 OpenAPI 명세를 바탕으로 만듭니다.

10/29에 범위를 줄이지 않고 전부 구현하기로 정하고 마감을 11/7로 옮겼습니다. 순서는 "포트폴리오의 핵심 주장(초과 예약 0건, 앱 3개에서도 정합성 유지)을 먼저 증명한다"를 기준으로 3단계로 나눴습니다.

### 다음 개선 (2차 외부 리뷰에서 이번에 하지 않은 것, 2026-11-18)

2차 외부 코드 리뷰의 1단계(설정·작은 코드)는 반영했다(6장 "예약 DB 실패 뒤 보상 판단"·"DB 시간 제한"·"저장소 장애 응답"·"Nginx 재시도", 2장 "Redis 비밀번호·메모리"). 아래는 설계를 바꾸거나 범위가 커서 이번에 하지 않은 것이다.

| 항목 | 지금 상태(한계) | 하려면 |
|---|---|---|
