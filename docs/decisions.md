# 결정 기록 (decisions.md)

[요구사항 정의서](./requirements.md)와 다르게 정했거나, 정의서가 열어 둔 질문에 답한 내용을 모읍니다. **정의서와 이 문서가 다르면 이 문서가 우선**합니다.

결정이 바뀌면 해당 항목을 고치고 맨 아래 "변경 이력"에 한 줄 남깁니다.

## 1. 기술 버전

| 항목 | 결정 | 이유 |
|---|---|---|
| Java | 21 (LTS) | 정의서와 동일. Boot 3.5와 검증된 조합 |
| Spring Boot | 3.5.16 | 3.x 라인의 마지막 오픈소스 릴리스(2026-06-25). 익숙한 3.x 생태계와 라이브러리 호환성을 우선 |
| 빌드 | Gradle 8.14.x (Kotlin DSL) | Boot 3.5가 지원하는 Gradle 8 라인으로 고정 |
| DB / 캐시 | MySQL 8.0, Redis 7 | 정의서와 동일 |

**Boot 3.5를 고르면서 감수한 것**

- 3.x는 오픈소스 지원이 2026년 6월 30일에 끝나, 이후 보안 패치가 무료로 나오지 않음. 1차 개발 범위에서는 영향이 없고, 2차 이후 Boot 4 마이그레이션을 별도 작업으로 검토
- start.spring.io는 지원 중인 버전(4.x)만 제공하므로, 빌드 파일은 직접 작성
- Java 21의 가상 스레드는 `synchronized` 블록 안에서 블로킹하면 캐리어 스레드에 고정(pinning)됨 → 락이 필요하면 `ReentrantLock` 사용
- QueryDSL은 3.5에서도 쓸 수 있지만 1차에서는 쓰지 않음 (아래 4장)

## 2. 저장소·개발 환경

| 항목 | 결정 |
|---|---|
| 저장소 구조 | 모노레포. `backend/`(Spring), `frontend/`(2차), `infra/`, `load/`, `docs/` |
| 로컬 인프라 | `compose.yaml`: MySQL·Redis만. 앱은 IDE에서 실행. Spring Docker Compose Support가 접속 정보를 자동 연결 (`spring.docker.compose.file=../compose.yaml`) |
| 앱 3개 구성 | `compose.full.yaml`: MySQL·Redis(compose.yaml과 같은 설정 + healthcheck)·app1~3(같은 이미지 `backend/Dockerfile`)·Nginx(`infra/nginx/nginx.conf`). 프로젝트 이름 `fivexbread-full`·볼륨을 개발용과 나누고 MySQL·Redis 포트는 열지 않아, 두 환경을 함께 띄워도 데이터·포트가 섞이지 않는다. 앱은 `docker` 프로필(아래 6장 "앱 3개 docker 프로필") |
| 비밀 값 | `.env`(git 제외)에 두고 `.env.example`에 키 이름만 커밋 |
| 사장님 초기 계정 | Flyway SQL이 아니라 `ApplicationRunner`로 생성. ADMIN이 없으면 `.env`의 `ADMIN_INITIAL_PHONE`·`ADMIN_INITIAL_PASSWORD`(BCrypt로 해시)로 만들고 `must_change_password=true`. 값이 비었거나 형식이 틀리면 앱은 띄우고 경고만 남김. 앱 여러 개가 동시에 떠도 MySQL `GET_LOCK`으로 한 명만 생성 |
| 테스트 손님 1,000명 | **마이그레이션이 아니라 `load/seed.sql`**(부하 테스트 전에 `load/run.sh`가 실행). 운영 마이그레이션에는 넣지 않는다. 이유는 6장 "부하 테스트 데이터" |
| 브랜치 | `main` 보호(PR로만 merge, squash merge). 작업 브랜치는 `feat/{기능ID}-{이름}`, `fix/`, `chore/`, `test/`, `docs/`. 서로 의존하는 기능 묶음은 대표 ID 하나로 브랜치를 만들고, 커밋은 기능 ID별로 나누며 PR 제목에 포함 ID를 모두 적는다 (예: feat/A-01-admin-stock → [A-01·A-04·A-02])        |

## 3. 시간 처리 규칙

| 위치 | 타입·형식 |
|---|---|
| DB | `DATETIME`, KST로 저장 |
| 엔티티 | `LocalDateTime` / `LocalDate` |
| API 요청·응답 | `OffsetDateTime`, `+09:00` 오프셋 포함 |
| 현재 시각 | 주입한 `Clock`(`ZoneId.of("Asia/Seoul")`)만 사용. `LocalDateTime.now()` 직접 호출 금지 |
| JVM 기본 시간대 | `Asia/Seoul`로 고정 (앱 `main`, 테스트 `user.timezone`). Hibernate의 `jdbc.time_zone` 변환이 JVM 시간대를 기준으로 하므로, UTC인 CI·컨테이너에서 `LocalDateTime`이 9시간 밀려 저장되는 것을 막는다 |

MySQL 컨테이너는 `--default-time-zone=+09:00`, 문자셋은 `utf8mb4`로 띄웁니다.

## 4. 1차 개발 범위 (2026-10-15 ~ 11-07)

백엔드 1차 범위 전체를 11/7까지 구현합니다. 프론트엔드는 2차에서 OpenAPI 명세를 바탕으로 만듭니다.

10/29에 범위를 줄이지 않고 전부 구현하기로 정하고 마감을 11/7로 옮겼습니다. 순서는 "포트폴리오의 핵심 주장(초과 예약 0건, 앱 3개에서도 정합성 유지)을 먼저 증명한다"를 기준으로 3단계로 나눴습니다.

일정이 밀리면 3단계 안에서 실시간 알림 → 캐시 무효화 → 정합성 점검 순으로 뒤로 미룹니다. 트랜잭셔널 아웃박스는 미루지 않습니다(취소·수량 변경의 Redis 반영을 보장하는 장치라 정합성 주장에 포함).

## 6. 요구사항 해석

정의서 문장만으로는 동작이 하나로 정해지지 않아 해석을 확정한 항목입니다.

| 항목 | 정의서 문장 | 확정한 해석                                                                                                                                                                                                                                                                                                                       |
|---|---|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| AU-05 로그인 실패 잠금 | 연속 5회 실패 시 10분 잠금. 성공하면 횟수 초기화. (5장 Redis 키 표: `login:fail:{phone}` TTL 10분) | `login:fail:{phone}`에는 시도 횟수(숫자)만 저장하고 로그인 성공 시 지운다. 방치된 키가 남지 않도록 만료 24시간을 걸고 횟수를 셀 때마다(잠긴 동안의 시도는 제외) 다시 늘린다. 24시간 동안 시도가 없으면 횟수도 사라진다(의도한 동작). 정의서의 TTL 10분은 잠금 시간으로 보고 `login:lock:{phone}`에 둔다(만드는 시점은 아래 "동시 요청"). 잠금은 연장하지 않으며, 잠긴 동안의 시도는 세지 않고 비밀번호도 비교하지 않고 423을 반환한다.                                             |

Redis를 내리면 앱마다 60초(명령 시간 제한) 뒤 `Unexpected error occurred in scheduled task` ERROR만 남고 그 회차는 실행되지 않으며 다시 시도하지 않는다 |

Content-Type은 `application/merge-patch+json`(다른 형식 415). 대상은 활성 손님만이고 없는 회원·사장님은 404. 제한이 없어도 200(멱등)이지만 이력은 실제로 지웠을 때만 `admin_action_log`에 `RESERVATION_BLOCK_CLEARED`로 남긴다. 응답은 `AdminMemberResponse`이고 회원 검색 응답에도 `reservationBlockedUntil`이 함께 나온다. 해제해도 노쇼 이력은 남아, 30일 안에 또 노쇼하면 바로 다시 제한된다 |
