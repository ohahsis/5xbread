# 결정 기록 (decisions.md)

[요구사항 정의서](./requirements.md)와 다르게 정했거나, 정의서가 열어 둔 질문에 답한 내용을 모읍니다. **정의서와 이 문서가 다르면 이 문서가 우선**합니다.

결정이 바뀌면 해당 항목을 고치고 맨 아래 "변경 이력"에 한 줄 남깁니다.

---

## 1. 기술 버전

| 항목 | 결정 | 이유 |
|---|---|---|
| Java | 21 (LTS) | 정의서와 동일. Boot 3.5와 검증된 조합 |
| Spring Boot | 3.5.16 | 3.x 라인의 마지막 오픈소스 릴리스(2026-06-25). 익숙한 3.x 생태계와 라이브러리 호환성을 우선 |
| 빌드 | Gradle 8.14.x (Kotlin DSL) | Boot 3.5가 지원하는 Gradle 8 라인으로 고정 |
| DB / 캐시 | MySQL 8.0, Redis 7 | 정의서와 동일 |

**Boot 3.5를 고르면서 감수한 것**

- 3.x는 오픈소스 지원이 2026년 6월 30일에 끝나, 이후 보안 패치가 무료로 나오지 않음. 1차 개발 범위에서는 영향이 없고, 2차 이후 Boot 4 마이그레이션을 별도 작업으로 검토
- start.spring.io는 지원 중인 버전(4.x)만 제공하므로, 빌드 파일은 직접 작성
- Java 21의 가상 스레드는 `synchronized` 블록 안에서 블로킹하면 캐리어 스레드에 고정(pinning)됨 → 락이 필요하면 `ReentrantLock` 사용
- QueryDSL은 3.5에서도 쓸 수 있지만 1차에서는 쓰지 않음 (아래 4장)

## 3. 시간 처리 규칙

| 위치 | 타입·형식 |
|---|---|
| DB | `DATETIME`, KST로 저장 |
| 엔티티 | `LocalDateTime` / `LocalDate` |
| API 요청·응답 | `OffsetDateTime`, `+09:00` 오프셋 포함 |

## 4. 1차 개발 범위 (2026-10-15 ~ 10-31)

예약 동시성과 앱 3개 분산 구성을 핵심으로 10/31까지 구현합니다. 프론트엔드는 2차에서 OpenAPI 명세를 바탕으로 만듭니다.

10/25에 마감을 10/31로 옮기면서 범위를 우선순위로 나눴습니다. 기준은 "포트폴리오의 핵심 주장(초과 예약 0건, 앱 3개에서도 정합성 유지)을 증명하는 데 필요한가"입니다. "포함"은 반드시 끝내고, "여유가 있으면"은 위에서부터 진행하다 10/30 저녁에 남은 항목을 "2차로 미룸"으로 옮깁니다.

### 포함

| 묶음 | 기능 |
|---|---|
| 환경 | Flyway V1·V2, 공통 예외(RFC 9457 + `code`), Testcontainers, GitHub Actions CI |
| 인증·회원 | C-01, AU-01~AU-10 (가입, 로그인 JWT + Refresh rotation, 실패 잠금, 권한), 사장님 초기 계정 |
| 사장님 관리 | A-01 빵 등록·수정·판매 중지, A-04 판매일 설정, A-02 수량 설정(R-07, ETag/If-Match) |
| 조회 | C-02 빵 목록(잔여는 DB 기준), 판매일·픽업 시간대 조회 |
| 예약 | C-04 예약(Redis Lua → DB 조건부 UPDATE → 보상, Idempotency-Key, 요청 제한), C-06·A-08 취소, C-05 내 예약 목록(단순 조회)·상세, A-06 수령 처리 |
| 분산 | 앱 3개 + Nginx 구성 (`compose.full.yaml`) |
| 테스트 | 동시 예약 1,000건 초과 0건, 예약·재고 관련 엣지 케이스 우선 (E-01~E-15 중 해당 항목) |

| 순서 | 기능 | 넣는 이유 |
|---|---|---|
| 1 | A-07 노쇼 처리 + R-17, ShedLock | 앱 3개에서 스케줄러가 한 번만 도는 것을 보여 주는 분산 핵심 |
| 2 | C-09·A-09 임시 비밀번호, C-10 비밀번호 변경 | 사장님 초기 계정의 `must_change_password` 강제를 완성 |
| 3 | C-03 실시간 잔여 알림 (WebSocket + Redis Pub/Sub) | 앱 3개에 흩어진 연결에 이벤트를 전파하는 구조. 작업량이 커서 마지막 |

| 정의서 | 1차 구현 | 이유 |
|---|---|---|
| 트랜잭셔널 아웃박스(`outbox_event`) | `@TransactionalEventListener(AFTER_COMMIT)`로 커밋 후 발행 | 실시간 알림(C-03)은 여유가 있을 때 진행하고, 정합성 점검(N-05)도 2차라 유실 복구 수단이 없음. 알림이 유실돼도 예약 정합성에는 영향이 없고 목록 조회로 최신 잔여를 볼 수 있음. 테이블은 V1에 만들어 두고 2차에서 적용 |
| QueryDSL (관리자 검색) | Spring Data JPA 쿼리 메서드·`@Query` | 1주 범위의 검색 조건이 단순해 설정 비용이 더 큼 |

| 예약 v1(DB만) vs v2(Redis) 비교 측정 | 바로 Redis 방식으로 구현 | 비교 측정은 2차 부하 테스트에서 |

## 6. 요구사항 해석

정의서 문장만으로는 동작이 하나로 정해지지 않아 해석을 확정한 항목입니다.

| 항목 | 정의서 문장 | 확정한 해석                                                                                                                                                                                                                                                                                                                       |
|---|---|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| AU-05 로그인 실패 잠금 | 연속 5회 실패 시 10분 잠금. 성공하면 횟수 초기화. (5장 Redis 키 표: `login:fail:{phone}` TTL 10분) | `login:fail:{phone}`에는 시도 횟수(숫자)만 저장하고 로그인 성공 시 지운다. 방치된 키가 남지 않도록 만료 24시간을 걸고 횟수를 셀 때마다(잠긴 동안의 시도는 제외) 다시 늘린다. 24시간 동안 시도가 없으면 횟수도 사라진다(의도한 동작). 정의서의 TTL 10분은 잠금 시간으로 보고 `login:lock:{phone}`에 둔다(만드는 시점은 아래 "동시 요청"). 잠금은 연장하지 않으며, 잠긴 동안의 시도는 세지 않고 비밀번호도 비교하지 않고 423을 반환한다.                                             |
| AU-05 동시 요청 | (정의서에 없음) | 비밀번호 비교 전에 시도 횟수를 먼저 센다. 횟수가 5에 닿는 시도는 비교를 시작하는 순간 `login:lock:{phone}`을 먼저 만들어, 그 뒤 들어온 요청은 비교하지 않고 423. 동시에 여러 요청이 와도 비교까지 가는 건 최대 5건(잠금 해제 후에는 1건). 잠금을 만든 시도가 틀리면 423으로 잠금을 유지하고, 맞으면 잠금과 횟수를 지우고 로그인. 비교 중이던 한도 안의 시도가 맞은 경우도 같다                                                                                        |
| AU-05 잠금 해제 후 | (정의서에 없음) | 횟수는 로그인 성공 때 또는 24시간 동안 시도가 없을 때만 사라지므로, 잠금(10분)이 풀린 뒤 다시 틀리면 바로 10분 잠금                                                                                                                                                                                                                                                      |
| 13-6 Refresh Token 재사용 감지 | 401 만료·재사용 감지 | 쿠키 값은 `{memberId}.{무작위 32바이트}`, Redis 키의 tokenId는 그 SHA-256. 재발급 때 GETDEL로 꺼내며 지우고 `refresh:used:{memberId}:{tokenId}`를 원래 남은 TTL만큼 남긴다. 이 기록이 있는 토큰이 다시 오면 재사용으로 보고 그 회원의 토큰을 전부 폐기한 뒤 401. 기록이 없으면(만료·위조·로그아웃) 401만 반환한다. memberId는 서명되지 않아, 키가 없다는 이유만으로 폐기하면 남의 세션을 끊을 수 있기 때문. 같은 토큰으로 동시에 재발급하면 1건만 성공하고 나머지는 재사용으로 처리된다. 전체 폐기를 해도 이미 발급된 Access Token은 남은 수명(최대 30분) 동안 유효하다(아래 "로그아웃"과 같은 한계) |
| AU-01 로그인 ID | 휴대폰 번호로 가입·로그인 | 회원을 가리키는 값은 `member.id`(JWT `sub`, 다른 테이블의 FK)이고, 전화번호는 로그인 조회에만 쓴다. 미가입 번호와 비밀번호 불일치는 같은 401·같은 문구로 응답한다. 본인 인증이 없어(Q-12) 남의 번호로 가입하거나 해지 번호가 재할당되는 문제는 알려진 한계. 가입 API는 이미 가입한 번호에 409 `DUPLICATE_PHONE`을 반환해 가입 여부가 드러나며, IP당 하루 가입 10회 제한(AU-02)으로 대량 확인만 막는다(알려진 한계)                                                                                                                                                              |
| 13-6 로그아웃 | Refresh Token 삭제, 쿠키 만료 → 204 (4단계) | Access Token은 남은 수명(최대 30분) 동안 유효하다. 쿠키가 없거나, 형식이 틀리거나, 이미 폐기된 토큰이어도 결과(로그아웃된 상태)가 같으므로 204와 만료 쿠키를 반환한다(멱등).                                                                                                                                                                                                                                                                                         |
| AU-10 로그 마스킹 | 로그에도 마스킹 | 번호는 `MaskedPhone`(010-\*\*\*\*-1234)으로만 남기고, 비밀번호·토큰 원문은 남기지 않는다. 비밀값을 담는 record(`IssuedTokens`, `AdminAccountProperties`)는 `toString`에서 값을 가린다. 우리 코드가 아닌 로그도 대상이다. Hibernate `SqlExceptionHelper`는 UNIQUE 위반 때 `Duplicate entry '01012345678'`을 ERROR로 남기므로, 번호 중복이 예상되는 곳은 오류 자체가 나지 않게 한다. 가입은 `INSERT IGNORE`로 넣고 0행이면 409 `DUPLICATE_PHONE`(`ON DUPLICATE KEY UPDATE`는 MySQL 드라이버가 찾은 행 수를 돌려줘 중복을 구분할 수 없어 쓰지 않음), 사장님 초기 계정은 `GET_LOCK`과 번호 사전 확인. `local` 프로필의 SQL 바인딩 TRACE 로그는 원문을 출력하지만 개발 PC 전용으로 허용하고, 테스트·운영 프로필에서는 쓰지 않는다 |
| 9장 daily_stock.version | 9장 데이터 모델 표: `daily_stock`에 `version`, `sale_date`에는 없음 | DDL·ERD·13-8을 따른다. 수량 ETag는 `sale_date.version` 하나이고 `daily_stock`에는 `version`을 두지 않는다. `daily_stock`은 예약이 `reserved_qty`를 자주 바꾸므로, 행 버전을 두면 예약이 몰릴 때 사장님 저장이 계속 충돌한다 |
